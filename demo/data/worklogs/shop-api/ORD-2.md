# ORD-2 주문 생성 · 재고 차감 (중복 주문 방지 · 동시성)
- 상태: 진행 중 · @claude · 시작 {{t:-3h}}

## 계획 (시작할 때 작성)
- 할 일: 장바구니 항목으로 주문을 만들고 재고를 차감한다. 같은 항목으로 결제 대기 주문이 두 개 생기지 않게 막는다.
- 범위 밖: 결제(PAY-2), 주문 알림(ORD-4)
- 완료 기준: 동시 주문 테스트에서 재고가 음수가 되지 않고, 중복 주문 요청은 409로 거절된다
- 관련 항목: 선행 ORD-1 · 이어지는 작업 ORD-4, PAY-2

## 무엇을 했나
주문 생성 API(`POST /api/orders`)를 만들었다. 재고 행을 잠근 뒤 차감하고, 같은 장바구니 항목의 결제 대기 주문이 있으면 409 `ORDER_ALREADY_PENDING`을 돌려준다.

## 왜 이렇게 했나
- **결정:** 재고는 비관적 락(`SELECT … FOR UPDATE`)으로 잠근다.
  - 이유: 인기 상품에서 낙관적 락은 재시도가 몰려 실패가 많다.
  - 버린 대안: 낙관적 락 + 재시도, Redis 분산 락(인프라 추가 부담)
- **결정:** 중복 주문은 주문 테이블의 유니크 제약이 아니라 조회로 막는다.
  - 이유: 취소된 주문은 같은 항목으로 다시 주문할 수 있어야 한다.

## 검증
- 실행: 동시 주문 100건 테스트 → 재고 10개 상품에서 성공 10건 · 품절 90건, 재고 0.
- 직접 확인하지 못한 것: 운영 DB와 같은 격리 수준에서의 대기 시간.

## 막혔던 문제와 해결
- 시도 1: 차감 쿼리에 `stock > 0` 조건만 추가 → 음수는 막았지만 주문은 만들어져 불일치가 남았다
- 시도 2: 재고 행을 먼저 잠그고 같은 트랜잭션에서 주문을 저장 → 100건 테스트 통과

## 학습 노트
### 비관적 락과 낙관적 락
- 쉽게 말하면: 비관적 락은 먼저 문을 잠그고 들어가는 것이고, 낙관적 락은 일단 들어갔다가 나올 때 누가 바꿨는지 확인하는 것이다.
- 정확히는: 비관적 락은 `SELECT … FOR UPDATE`로 행을 잠가 다른 트랜잭션을 기다리게 한다. 낙관적 락은 버전 열을 비교해 바뀌었으면 실패시킨다.
- 왜 여기서 필요했나: 재고 1개 상품에 주문이 동시에 들어오면 둘 다 "재고 있음"으로 읽었다.
- 대안과 비교: 충돌이 드물면 낙관적 락이 빠르고, 충돌이 잦으면 재시도 비용 때문에 비관적 락이 낫다.
- 우리 코드에서: `StockRepository.findForUpdate`.
- 흔한 함정: 잠그는 순서가 다르면 교착이 난다. 항상 상품 ID 순으로 잠근다.
- 스스로 확인할 질문: 주문 하나에 상품이 세 개면 어떤 순서로 잠가야 하는가?

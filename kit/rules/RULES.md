# 공통 작업 규칙 (Claude · GPT)

에이전트를 바로잡을 일이 생기면 이 문서에 줄을 더하지 않고 검사(린터 · 훅 · 테스트)나 명령으로 만든다. 훅이 막으면 메시지의 "→" 뒤대로 한다.

**개인 규칙:** `~/.work-dash/RULES.local.md`가 있으면 이 파일 바로 뒤에 읽고 따른다. 부딪히면 그 파일을 따른다. 허락 없이 진행할 범위, 위임 기준처럼 사람마다 다른 규칙은 거기에 쓴다. 이 파일은 기록 도구 저장소가 원본이라 직접 고치지 않는다.

## 로드맵 · 작업 카드
- 항목 · 작업 카드 · 이슈는 `node ~/.work-dash/app/core/item.js`로 다룬다(`--help`). 인자 없이 부르면 프로젝트 이름(`<프로젝트>`)과 현황이 나온다.
- 설계 · 정의 · 요구사항 정리도 로드맵 항목(정의서 항목)으로 잡고, 결과는 그 항목의 작업 카드에 쓴다. 완료할 때(커밋 전이어도) `done`으로 마무리한다.
- 묶인 프로젝트에서는 항목 하나가 저장소 하나 안에서 끝나게 자르고, 커밋 · PR은 저장소별로 한다.
- 항목 · 마일스톤을 새로 짤 때만 `~/.work-dash/ROADMAP-FORMAT.md`의 해당 절을 읽는다. 다른 프로젝트의 로드맵을 본보기로 삼지 않는다.

## 이슈
- 작업 중 발견한 문제는 로드맵이 아니라 이슈로 적는다: `item.js issue add …`. 다른 프로젝트 · 팀원 코드의 문제를 어디에 적는지는 `item.js --help`의 이슈 줄에 있다.

## 무엇을 어디에 쓰나
| 내용 | 위치 |
|---|---|
| 할 일 · 진행 상태 · 확정된 결정 요약 | 로드맵 (`roadmaps/<프로젝트>.md`) |
| 설계 · 정의 · 결정 근거 · 작업 기록 | 그 항목의 작업 카드 (`worklogs/<프로젝트>/<ID>.md`) |
| 발견한 문제 | 이슈 파일 (`issues/<프로젝트>.md`) |
| 동작 흐름 | 흐름 문서 (`flows/<프로젝트>.md`) |
| 전후를 비교할 수 있는 개선 · 오래 걸린 문제 해결 | 개선 기록 (`improvements/<프로젝트>.md`) — 쓰기 직전에 `IMPROVEMENTS-FORMAT.md`를 읽는다 |
| 팀과 공유할 산출물 (ERD, API 문서 등) | 프로젝트 저장소 `docs/` — **사용자가 요청할 때만** |

- 진행 상태는 에이전트 메모리가 아니라 로드맵과 작업 카드에 남긴다. 메모리에는 사용자 선호와 피드백만 둔다.
- 다른 항목 · 이슈 · 문서는 ID(`CART-2`, 다른 프로젝트는 `BE:MAT-11`, 이슈는 `CART-2#1`)나 저장소 기준 경로(`docs/erd.md`, 절은 `§4.7`)로 가리킨다. "앞의 설계"처럼 ID 없이 가리키지 않는다.

## 동작 흐름 문서
- 프로젝트 구조를 파악할 때 코드를 훑기 전에 `item.js flow <고칠 파일 경로|항목 ID>`를 본다.
- 작업이 흐름을 바꿨는지는 항목을 완료할 때 명령이 알린다.

## 확인
- 확인은 `node ~/.work-dash/app/core/check.js`로 돌린다. 전체(`--full`)는 원격에 푸시 · PR 하기 직전에만 돌린다.
- 서버 · 앱을 띄우는 확인은 지휘(메인) 세션이 맡는다. 하위 세션은 브랜치 · 확인할 동작 · 기대 결과를 지휘 세션에 보낸다.

## 커밋 · 위임
- Codex는 커밋 · 푸시 · PR 직전에 `~/.work-dash/RULES-COMMIT.md`를, 일을 맡기기 직전에 `~/.work-dash/RULES-DELEGATE.md`를 읽는다. Claude는 그때 훅이 보여 준다.
- 새 세션은 이 파일을 스스로 읽는다. 규칙을 브리핑에 옮겨 적지 말고 맡길 로드맵 항목 ID만 준다. 항목이 없으면 로드맵에 잡은 뒤 맡긴다.

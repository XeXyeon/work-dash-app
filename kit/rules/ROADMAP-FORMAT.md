# 로드맵 형식과 동작 (Claude · GPT 공통)

Claude의 `/roadmap` 커맨드와 Codex의 `roadmap` 스킬이 모두 이 파일을 따른다.

## 로드맵 파일
- 위치: `~/.work-dash/roadmaps/<프로젝트 이름>.md`. 개인용이며 저장소에 만들거나 커밋하지 않는다. `work-dash` 앱의 로드맵 화면이 이 파일을 읽는다.
- 줄의 모양(상태 기호 · ID 번호 · 담당 태그 · 메모 머리말)은 아래 "명령으로 바꾼다"의 명령이 쓴다. 손으로 쓴 줄이 틀리면 문서 검사가 고칠 방법을 알려 준다(Claude는 훅이 바로, 그 밖에는 `node ~/.work-dash/app/core/doclint.js <파일>`). 모양은 "항목 쓰는 법"의 예시 하나를 본다.
- 상태: `[ ]` 할 일, `[~]` 진행 중, `[x]` 완료, `[!]` 외부 대기, `[>]` 보류, `[-]` 취소. 뒤의 셋은 "지금 하지 않는 항목"을 따른다.
- 선행 관계 `(after: ID, ID)`에는 진짜로 먼저 끝나야 하는 것만 적는다. 내가 맡은 다른 로드맵의 항목은 `<접두어>:<ID>`로 적는다(예: `BE:MAT-11`). 접두어는 `~/.work-dash/config.json`의 `projects.<프로젝트 이름>.key`이고, 없으면 프로젝트 이름 전체다.
- 한 번 붙인 ID는 바꾸지 않는다. 줄 끝의 완료 시각 `✓…`은 work-dash가 붙이니 붙이거나 지우지 않는다.

## 항목 쓰는 법
문법은 위와 같고, 아래는 항목을 **어떤 크기와 말투로** 쓰는지에 대한 규칙이다. 다른 로드맵 파일을 참고하지 말고 이 절만 따른다.

- **항목 한 줄 = 결과물 이름 + 범위.** `ID 결과물 이름 (포함 범위 · 포함 범위) (after: …)`. 이름은 명사구로 쓰고 동사로 끝내지 않는다(`주문 취소 API`, `주문 취소하기` ✗). 괄호 안에는 이 항목이 포함하는 것을 ` · `로 나열한다.
- **항목 크기 = 작업 카드 하나.** 한 번 시작해서 검증까지 끝낼 수 있는 크기로 자른다. 엔티티 · 리포지토리 · API · 테스트를 한 항목에 다 넣지 말고, 기능 하나가 여러 날 걸리면 나눈다.
- **설계 · 정의도 항목이다.** 구현 전에 정할 것이 있으면 `<접두어>-N <대상> 정의서 (핵심 쟁점 · 쟁점)` 또는 `<대상> 요구사항 정의` 항목을 먼저 두고, 구현 항목이 `(after:)`로 그것을 가리킨다. 정의 내용은 그 항목의 작업 카드에 쓴다(아래 "정의 · 설계 항목의 카드"). 저장소에 별도 설계 문서를 만들지 않는다.
- **접두어 = 도메인.** 영문 대문자 2~4자(`CART`, `ORD`, `AUTH`). 무엇에 관한 일인지를 말한다. 프로젝트 이름과 기술 층(`WEB` · `FE` · `BE`)은 접두어로 쓰지 않는다. 같은 주제의 후속 마일스톤은 접두어와 번호를 이어 쓴다. 접두어 하나가 프로젝트 항목의 절반을 넘으면 나눈다. 공통 접두어는 `OPS`(커밋 · 병합 · 배포 · 설정) · `DOC`(문서)만 둔다.
- **메모 줄은 `memo <ID> <머리말> "<한 줄>"`로 단다.** 상세 근거는 카드에 두고 로드맵에는 한두 줄 요약만 올린다. 앞선 결정을 뒤집을 때는 원래 `결정` 줄을 지우지 않고 `재설계(YYYY-MM-DD, 새 ID): …`를, 완료된 항목의 구현이 나중 항목으로 대체됐으면 `<새 ID>에서 교체: …`를 손으로 쓴다(4칸 들여쓰기).

예시 (형식과 말투만 본다):

```markdown
## M2. 사이트 안 알림
    완료 기준: 주문 이벤트가 나면 받는 사람의 알림 목록에 1건이 보이고, 수신 거부한 사람에게는 가지 않는다
- [x] NTF-1 알림 정의서 (대상 이벤트 · 수신 거부 · 하루 상한 · 저장 방식)
    결정(2026-10-28): 사이트 안 알림만, 이벤트당 수신자 1건 멱등 저장, 하루 상한 20건
    결정(2026-10-28): 푸시 · 이메일은 범위 밖 (NTF-6으로 보류)
- [x] NTF-2 알림 저장 · 멱등 발행 (notification 테이블 · 이벤트 리스너) (after: NTF-1)
- [~] NTF-3 내 알림 조회 · 읽음 처리 GET /api/notifications (after: NTF-2) @claude
- [!] NTF-4 수신 거부 설정 (after: NTF-2)
    대기: 회원 설정 화면 담당자와 필드 이름 협의
- [>] NTF-6 푸시 알림 (after: NTF-3)
    결정(2026-10-28): 보류 — 사이트 안 알림을 운영해 본 뒤 정한다
```

## 마일스톤 나누는 법
마일스톤은 주제 폴더가 아니라 **끝이 있는 지점**이다. 하위 세션 하나가 맡아 시작부터 끝까지 가는 단위이기도 하다.

- **마일스톤 하나 = 끝나면 직접 확인할 수 있는 결과 하나.** 만들기 전에 "이게 끝나면 무엇을 해 볼 수 있나?"에 한 문장으로 답한다. 답이 동작이나 상태면 마일스톤이다. 답이 "관련 작업이 정리된다" · "남은 것을 처리한다"면 마일스톤이 아니다.

| 유형 | 답의 모양 | 예 |
|---|---|---|
| 기반 | 설계가 확정돼 구현을 시작할 수 있다 / 프로젝트가 빌드 · 실행 · 배포된다 | `설계` — 정의서가 확정됐다 · `프로젝트 기반` — 로컬에서 서버와 화면이 뜨고 로그인된다 |
| 기능 | 사용자가 무엇을 할 수 있다 | `공동물품 공동구매` — 방을 만들어 N빵 결제까지 간다 |
| 전환 · 정비 | 시스템이 어떤 상태가 됐고 무엇으로 확인된다 | `order-service 물리 분리` — order-service가 단독으로 뜨고 테스트가 통과한다 |

- **이렇게 나누지 않는다.** 기술 계층(`엔티티`, `API`), 상대(팀원 · 다른 모듈별 `연동`), 기간(`1주차`), 잡동사니(`마무리`, `후속`, `기타`). 누구와 맞추는지는 `협의:` · `연결:` 메모로, 기간은 마감 `(~11/04)`으로 쓴다.
- **제목은 결과 이름만.** 명사구로 짧게 쓴다. 상태(`폐기`, `실험`) · 결정 요약 · 범위 나열을 제목에 넣지 않는다.
- **완료 기준 한 줄.** 제목 바로 아래 `    완료 기준: …`에 무엇으로 확인하는지 쓴다(해 볼 동작, 통과할 테스트 · 명령). 이 줄이 하위 세션의 목표이자 끝나는 조건이다.
- **크기는 3~8항목이 기준.** 세션 하나 · PR 한두 개로 끝낼 크기다. 완료 기준이 하나면 넘어도 두고, 완료 기준이 둘로 갈리면 나눈다. 한두 항목짜리 작업은 마일스톤으로 따로 만들지 않고 그 항목이 기여하는 마일스톤에 둔다. 범위가 정해진 기능 묶음은 항목이 적어도 마일스톤으로 둔다.
- **번호는 만든 순서.** 한 번 붙인 번호는 바꾸지 않는다(작업 카드와 흐름 문서가 번호를 가리킨다). `M11b` 같은 접미사를 쓰지 않고 다음 번호를 쓴다. 파일 안의 순서는 진행 순서로 두며 번호 순서와 달라도 된다.
- **닫힌 마일스톤 = 할 일 · 진행 중 항목이 없는 마일스톤.** 외부 대기 · 보류 · 취소 항목은 닫힘을 막지 않는다. 대시보드는 닫힌 마일스톤을 자동으로 접는다.
- **닫힌 마일스톤은 다시 열 수 있다.** 새 항목이 그 마일스톤의 완료 기준 안에 들면(빠뜨린 부분, 완료 기준을 아직 못 채운 부분, 같은 결과의 후속 · 개선) 그 마일스톤에 추가해 다시 연다. 다시 열 때는 사용자에게 "M<번호>를 다시 엽니다"라고 한 줄로 알린다. 완료 기준을 넘어서는 새 결과면 새 마일스톤으로 만든다(`어뷰징 탐지` → `어뷰징 탐지 고도화`). 외부 대기 · 보류 항목을 다시 시작해도 마일스톤이 다시 열린다.
- **항목은 소속 마일스톤을 떠나지 않는다.** 기다리거나 미루거나 하지 않기로 한 항목도 그 기능의 마일스톤에 그대로 두고 상태로 표시한다. `나중` · `대기` · `보류` 같은 모음 구역을 만들지 않는다.

### 지금 하지 않는 항목
| 기호 | 상태 | 쓰는 때 | 명령 |
|---|---|---|---|
| `[!]` | 외부 대기 | 내 작업이 아닌 것(팀원 · 다른 팀 · 인프라)을 기다린다 | `wait` |
| `[>]` | 보류 | 사용자가 미루기로 했다 | `hold` |
| `[-]` | 취소 | 사용자가 하지 않기로 했다 | `drop` |

- 내 로드맵 안의 다른 항목을 기다리는 것은 상태가 아니라 `(after: ID)`로 쓴다(대시보드가 "선행 필요"로 계산한다). 내가 맡은 다른 로드맵의 항목을 기다리는 것도 `(after: <접두어>:<ID>)`로 쓴다. 외부 대기는 가리킬 ID가 없는 기다림에만 쓴다.
- 보류와 취소는 사용자 결정이다. 에이전트가 판단해서 붙이지 않고, 사용자에게 물어 확정된 뒤에 붙인다. 외부 대기는 기다리는 상대와 내용이 확인되면 붙인다.
- 다시 시작할 때는 `reopen`(할 일로) 또는 `start`(바로 진행 중으로)를 쓴다.
- 선행 계산: `(after:)`가 가리키는 항목이 완료 또는 취소면 풀린 것으로 본다. 외부 대기 · 보류면 뒤 항목은 여전히 선행 필요다.
- 진행률: 완료 수 ÷ (전체 − 보류 − 취소). 외부 대기는 남은 일이라 분모에 넣는다.

### 소속 마일스톤이 없는 것
- 특정 기능의 후속 · 개선이면 그 기능의 마일스톤에 둔다(닫혔으면 다시 연다. 완료 기준을 넘어서면 새 마일스톤으로).
- 아직 시작하지 않은 기능 묶음이면 마일스톤을 만들고 항목을 보류로 둔다.
- 문서 · 운영 같은 공통 작업은 결과가 있는 공통 마일스톤(`문서`, `배포`)에 둔다.
- 범위가 없는 정리(`리팩토링`, `코드 정리`)나 아직 계획이 아닌 아이디어는 로드맵 항목이 아니다. 이슈 파일에 개선 · 기술 부채로 적는다(`~/.work-dash/ISSUES-FORMAT.md`).

## 명령으로 바꾼다
항목 상태 · 담당 태그 · 다음 ID · 카드 틀 · 상태 줄의 시각은 손으로 쓰지 않고 명령이 쓴다. 프로젝트는 현재 폴더로 찾는다(다른 프로젝트는 `--project <이름>`). Codex는 `--as gpt`를 붙인다.

```bash
node ~/.work-dash/app/core/item.js              # 현황 · 다음에 시작할 항목(위에서부터 추천)
node ~/.work-dash/app/core/item.js start <ID>   # [~] + 담당 태그 + 작업 카드
node ~/.work-dash/app/core/item.js done <ID>    # [x] + 카드 마무리. 커밋한 뒤에는 --committed
node ~/.work-dash/app/core/item.js --help       # add · milestone · wait · hold · drop · reopen · memo · section · extra · issue
```

- 명령이 막으면 `→` 뒤에 적힌 대로 한다. `--force`는 사용자가 진행하라고 했을 때만 붙인다.
- `add`: 넣을 마일스톤은 직접 고른다. 맞는 곳이 둘 이상이면 진행 중 항목이 있는 쪽, 그것도 같으면 뒤쪽 마일스톤에 넣고, 어디에 넣었는지와 건 선행을 한 줄로 알린다. 맞는 곳이 없으면 새 마일스톤(제목 · 완료 기준)을 제안하고, 범위가 없는 정리나 아이디어면 이슈로 적자고 제안한다.
- `init`(명령 없음): 파일이 이미 있으면 덮어쓰지 않고 알린다. 없으면 README, docs/, 최근 git log, 열린 이슈를 훑어 사용자가 맡은 범위를 파악하고, 모르는 것은 묻는다. 초안을 보여 주고 확인을 받은 뒤 파일을 만든다.
- 메모 줄처럼 명령이 없는 것을 손으로 고칠 때는 고칠 줄만 다시 읽고 그 줄만 고친다. 다른 에이전트가 `[~]`로 잡은 항목은 사용자가 시킬 때만 바꾼다.

## 작업 카드
항목을 시작할 때 만들고(`start`), 작업하면서 채우고, 완료할 때 마무리하는(`done`) 작업 기록이다. 나중에 대화 기록을 다시 읽지 않고도 "무엇이 바뀌었고 왜 그렇게 했는지"를 알 수 있어야 한다. 커밋을 기다리지 않는다.

- 위치: `~/.work-dash/worklogs/<프로젝트 이름>/<ID>.md`. 개인용이며 저장소에 커밋하지 않는다. `work-dash`의 작업 상세 화면 맨 위에 보인다.
- 틀은 명령이 만든다. `<채울 것: …>` 줄을 채우고 해당 없는 줄은 지운다. 채우지 않은 줄이 남으면 `done`이 완료를 막는다.
- **진행 중에 바로 쓴다.** 결정을 내렸거나, 파일을 크게 바꿨거나, 막혔다가 풀렸을 때 해당 절을 갱신한다. 카드만 봐도 지금 어디까지 왔는지 알 수 있어야 한다.
- 추측으로 채우지 않는다. 직접 확인한 것만 쓰고, 확인하지 못한 것은 그렇다고 쓴다.
- **실패할 때마다 시도를 적는다.** 테스트 · 빌드 · 실행이 실패해 고쳤는데 같은 증상이 다시 나오면, 다음 시도 전에 `막혔던 문제와 해결`(없으면 `section <ID> "막혔던 문제와 해결"`)에 `- 시도 N: 무엇을 바꿨나 → 결과` 한 줄을 적는다. 같은 증상에 서로 다른 시도가 두 줄 쌓였으면 **그 문제는 세 번째를 시도하지 않고 보고한다.** 시도한 방법과 결과, 원인 가설을 모아 사용자(또는 지휘 세션)에게 낸다. 그 문제와 무관한 작업은 계속한다. 보고를 받은 쪽이 기록을 보고 재현 정보 · 로그를 더 모을지, 설계를 다시 판단할지 정한다(두 번은 멈춤이 아니라 보고 기준이다). Claude 세션에서는 같은 명령이 연속으로 실패하면 work-dash 훅도 경고를 돌려준다.
- 이 작업이 동작 흐름을 새로 만들었거나 바꿨으면, `~/.work-dash/flows/<프로젝트 이름>.md`가 있을 때 **해당 흐름 절만** 갱신한다(`~/.work-dash/FLOWS-FORMAT.md`의 갱신 규칙).
- 커밋한 뒤에는 `done <ID> --committed --commit "<해시> <제목>"`으로 카드를 `완료`로 바꾼다.
- 완료한 항목에 작은 일을 더할 때는 `extra <ID>`로 카드에 `## 추가 작업` 절을 붙인다. 로드맵 항목은 `[x]` 그대로다. 결과가 따로 있는 후속 작업이면 새 항목으로 만든다.
- 맡긴 항목의 카드를 누가 쓰는지는 `RULES-DELEGATE.md`를 따른다. 여러 항목을 맡겨도 항목마다 카드가 따로 생겨야 한다.

### 정의 · 설계 항목의 카드
정의서 · 요구사항 정의 항목은 코드보다 **결정**이 결과물이다. 카드가 그 결정의 원본 문서가 된다.

- `section <ID> <절>`로 진행 순서대로 더한다: `코드에서 확인한 사실` → `제안`(또는 `정의서`) → `확인하지 못한 가정` → `열린 질문` → `확정 사항` → 방향이 바뀌면 `방향 전환 --by <누구>`. 확정될 때마다 바로 적고, 이미 적은 절은 고쳐 쓰지 않고 아래에 이어 쓴다.
- 완료할 때: `바뀐 것`은 "코드 변경 없음", `검증`은 "사용자 확정"과 확정 시각을 쓰고 `done <ID> --committed --note "정의서 항목이라 커밋 없음"`으로 끝낸다.
- 완료하면 핵심 결정을 로드맵 항목 아래 `결정(날짜):` 줄로 한두 줄 요약해 올린다.

# 주요 결정과 문제 해결

만드는 동안 항목마다 작업 카드에 "무엇을 정했고, 왜 그랬고, 무엇을 버렸는지"를 남겼습니다. 그 가운데 설계에 영향이 컸던 것만 골라 다시 썼습니다. 숫자는 그때 잰 값이고, 재지 않은 것은 추정이라고 적었습니다.

전체 진행은 [개발 로드맵](roadmap.md)에 있습니다.

## 결정

### 1. 전부터 쓰던 마크다운 파일을 그대로 원본으로 삼는다
- **출발점:** 이 앱을 만들기 전에 이미 로드맵 · 이슈 · 작업 카드를 마크다운 파일로 쓰고 있었고, 그것을 읽는 파서와 터미널 화면이 있었다.
- **결정:** 앱을 위해 저장소를 따로 두지 않는다. 같은 파일을 원본으로 삼고, 서버는 있던 파서를 그대로 불러 쓴다.
- **이유:** 기록을 쓰는 쪽이 에이전트이고, 사람도 같은 파일을 에디터로 열어 고친다. 앱이 꺼져 있어도 기록은 계속 쌓인다.
- **따라온 것:** 해석 규칙이 한 곳(파서)에만 있어야 한다. 서버 · 훅 · 명령이 모두 같은 파서를 쓴다.

### 2. 서버는 Node 내장 `http`와 파일 감시, 화면 갱신은 SSE
- **결정:** 프레임워크 없이 Node 내장 `http`로 API와 정적 파일을 함께 내고, 파일이 바뀌면 SSE로 화면에 알린다. 화면은 Vite + React + TypeScript, 서버 상태는 TanStack Query가 맡고 SSE 신호를 받으면 다시 읽는다.
- **이유:** 읽기 API 몇 개와 "바뀌었다" 신호 하나면 되는 크기였다. 신호가 서버에서 화면으로만 가므로 WebSocket이 필요 없다.
- **버린 대안:** 프레임워크 없는 HTML + JS. 더 가볍지만 화면이 커지면 불편하다고 보고 React를 골랐다.
- **지킨 것:** 서버는 `127.0.0.1`에만 연다. 처음에는 읽기 전용으로 시작했고, 뒤에 더한 쓰기 · 실행 API는 다른 출처에서 온 요청을 거절한다.

### 3. 데스크톱 앱은 Tauri, 백엔드는 Node 그대로
앱 틀과 백엔드를 따로 비교했습니다.

| 앱 틀 | 장점 | 단점 |
|---|---|---|
| **Tauri 2 (선택)** | 앱 용량 수 MB, macOS 내장 웹뷰 사용, 트레이 · 알림 플러그인 | 웹뷰가 Safari 엔진 |
| Electron | Node 파서를 앱 안에서 바로 씀 | 용량 100MB 이상, 메모리 많음 |
| 순수 Rust GUI | 가장 가벼움 | 만든 React 화면을 버리고 다시 만들어야 함 |

| 백엔드 | 장점 | 단점 |
|---|---|---|
| **Node 서버 유지 (선택)** | 해석 규칙이 한 곳, 코드 그대로 | Node가 설치돼 있어야 함 |
| Rust로 재작성 | 앱 하나로 동작 | 같은 규칙을 JS · Rust 두 벌로 관리 |

- **결정:** Tauri 앱은 창과 메뉴 막대만 맡고, 떠 있는 Node 서버를 쓰거나 없으면 띄운다.
- **이유:** 그때 잰 Node 서버는 메모리 30 ~ 68MB(RSS), 가만히 있을 때 CPU 0%, 응답 1 ~ 7ms였다. Rust로 옮겨 얻는 것은 사람이 느끼지 못하는 응답 시간과 메모리 약 50MB(추정)였고, 잃는 것은 "형식이 바뀔 때마다 두 곳을 고친다"였다. 훅과 명령이 Node 파서를 계속 쓰므로 Node가 없어지지도 않는다.
- **미룬 것:** 앱이 생긴 뒤 웹뷰까지 포함한 전체 메모리를 재서 다시 판단하기로 했다. 그것이 4번이다.

### 4. Rust로 다시 쓰기 전에 먼저 잰다
3번에서 "웹뷰가 훨씬 커서 서버는 앱 전체의 일부일 것"이라고 예상했습니다. 재 보니 틀렸습니다.

| 상태 | 앱 본체 | 웹뷰 | Node 서버 | 합계 | Node 비중 |
|---|---|---|---|---|---|
| 가만히 | 32 | 80 | 72 | 184 | 39% |
| 요청 150번 직후 | 32 | 82 | 104 | 218 | 48% |
| 요청 900번 더 | 32 | 82 ~ 83 | 117 → 120 | 233 ~ 235 | 51% |

(단위 MB. macOS `footprint` 기준이라 3번의 RSS 값과 바로 견줄 수는 없다. 웹뷰 프로세스는 시스템이 알려 주는 소속으로 가렸다)

- **확인한 것:** Node 서버가 앱 전체에서 가장 큰 덩어리였다. 그런데 요청 1,200번 뒤 강제로 가비지 수집을 하면 살아 있는 데이터는 약 10MB였다. 서버가 캐시를 붙들고 있는 것은 아니었다.
- **추정한 것:** 서버는 요청마다 로드맵 · 이슈 파일을 새로 읽고 해석해서 버린다. 그 자리를 V8이 잡아 둔 채 돌려주지 않아 커지는 것으로 보인다. 캐시를 넣고 다시 재는 데까지는 가지 않았고, 시작할 때 잠깐 150MB까지 오르는 까닭도 찾지 못했다.
- **판단:** Rust로 옮기기 전에 Node 서버에서 줄일 수 있는 만큼 줄여 보고, 그래도 차이가 크면 그때 전환을 정하는 순서가 맞다고 봤다.
- **여기까지 했다:** 전환 여부를 정하기 전에 앱을 멈췄다. Rust 서버의 메모리는 재지 않았다.
- **배운 것:** 예상은 재 보니 틀렸고, 비중이 크다는 것만으로 원인이 정해지지도 않았다. Node 서버의 비중만 보고 다시 썼다면 읽는 방식이라는 더 싼 후보를 건너뛰었을 것이다.

### 5. 규칙을 글에서 검사로 옮긴다
- **출발점:** Lauren Tan의 발표 "All Code Is Slop (Except Mine)"에서 가져온 생각이다. 에이전트가 지킬 것은 글이 아니라 검사로 둔다.
- **문제:** 에이전트에게 준 규칙 문서가 계속 길어졌다. 길어질수록 세션마다 읽는 비용이 늘고, 그래도 지켜지지 않는 줄이 있었다.
- **결정:** 에이전트를 바로잡을 일이 생기면 규칙 문서에 줄을 더하지 않고 검사(린터 · 훅 · 테스트)나 명령으로 만든다.
- **어떻게:**
  - 형식 규칙은 문서 린터로 옮기고, 그 파일을 고친 직후의 훅에서 돌린다.
  - 오류 메시지에 무엇이 틀렸는지와 **어떻게 고치는지**를 함께 적는다. 그 문장이 규칙 문서의 줄을 대신한다.
  - 판단에 맡기는 문장("크면", "필요하면")은 숫자 기준이나 금지로 바꾸고, 둘 다 안 되면 지운다.
  - 틀린 적 없는 규칙을 미리 검사로 만들지 않는다. 실제로 틀렸던 것부터 하나씩 쌓는다.
- **갈린 선택:** 문서 검사는 쓰기를 막지 않고 오류를 돌려줘 고치게 한다(작업이 끊기지 않게). 커밋 · PR 앞 검사는 걸리면 명령을 막는다(밖으로 나가면 되돌리기 어려우므로).

### 6. 막는 훅에는 대신 쓸 길을 함께 준다
- **문제:** 에이전트가 수십 KB짜리 로드맵을 통째로 읽곤 했다. 한 번 읽을 때 수만 토큰이 드는 크기다(크기로 어림한 값이고 재지는 않았다).
- **결정:** 20KB를 넘는 로드맵 · 이슈 · 흐름 문서를 범위 없이 읽으면 훅이 막고, 같은 메시지에서 항목 하나 · 마일스톤 하나만 보여 주는 명령을 알려 준다.
- **이유:** 막기만 하면 에이전트는 다른 길(`cat`, 쪼개 읽기)로 같은 양을 읽는다. 필요한 것만 주는 길이 더 쉬워야 한다.
- **남긴 것:** 전체를 봐야 하는 세션을 위해 이유를 대고 여는 명령을 두었고, 쓴 기록이 남는다.

### 7. 반복 실패는 막지 않고 경고한다
- **결정:** 한 세션에서 같은 계열의 명령이 연속 세 번 실패하면 "멈추고, 시도를 적고, 보고하라"는 문구를 모델에게 돌려준다. 명령을 막지는 않는다.
- **이유:** 훅이 셀 수 있는 것은 "같은 문제"가 아니라 "같은 명령의 연속 실패"다. 테스트를 하나씩 고쳐 가는 정상적인 반복도 걸리므로 막으면 방해가 된다.
- **세부:** 명령을 통째로 비교하지 않고 앞 두 낱말로 묶는다. 막힌 모델은 인자를 조금씩 바꿔 가며 다시 돌리기 때문에 통째로 비교하면 매번 다른 명령으로 보인다.

### 8. 푸시 앞 전체 확인은 커밋이 아니라 tree 해시로 본다
- **결정:** 전체 확인이 통과하면 그때 작업 트리의 tree 해시를 적어 두고, `git push`를 보면 `HEAD`의 tree가 그 기록에 있는지 확인한다. 없으면 막는다.
- **이유:** 확인한 뒤 커밋하는 순서라, 확인하는 시점에는 커밋 해시가 아직 없다. tree 해시는 내용이 같으면 같다.

### 9. 화면에서 로컬 앱을 여는 길은 서버 하나로 모은다
세션 카드의 "대화 열기"는 Claude 앱 · ChatGPT 앱 · iTerm을 엽니다. 로컬에서 명령을 실행하는 API라서 조심한 부분입니다.

- 셸을 거치지 않는다. `execFile`에 인자 배열로 넘기고, 세션 ID는 정규식으로 형식을 확인한 뒤에만 쓴다.
- iTerm은 AppleScript 소스에 값을 이어 붙이지 않고 인자로 넘겨 셸 인용을 맡긴다.
- 세션의 작업 폴더 경로는 서버 안에서만 쓰고 API 응답에는 넣지 않는다.
- **버린 대안:** 화면에서 앱 링크를 직접 열기. 웹뷰가 사용자 정의 스킴을 막을 수 있고, iTerm은 어차피 서버가 필요해서 한 길로 통일했다.

### 10. 기록 도구를 앱에서 떼어 낸다
- **문제:** 규칙 · 파서 · 훅이 앱 저장소 안에 있어서, 기록하는 일이 화면을 보여 주는 앱에 묶여 있었다.
- **결정:** 기록 도구(규칙 문서 · 파서 · 훅 · 명령)를 별도 저장소로 떼어 내고, 앱은 그것을 읽기만 한다. 이 저장소의 `kit/`은 그 시점의 사본이다.
- **계기:** 평소 쓰는 에이전트 앱의 사이드바에 같은 보기를 플러그인으로 만들어 보니, 이 앱은 기록을 보는 여러 화면 가운데 하나가 됐다. 그렇다면 기록하는 쪽이 어느 한 화면에 들어 있을 이유가 없었다.
- **결과:** 떼어 낸 뒤 화면은 플러그인 쪽을 쓰기로 했고, 이 앱은 여기서 멈췄다.

## 문제 해결

### 압축 버튼이 쓰던 글을 그대로 전송했다
- **문제:** 세션 카드의 압축 버튼을 누르면 `/compact`가 아니라 입력창에 쓰던 글이 전송됐다. 3번 시도해 3번 모두였다.
- **원인(추정):** 한글 입력 상태에서는 글자로 보낸 단축키(⌘A · ⌘X · ⌘V)가 듣지 않고 Enter만 들었다.
- **해결:** 단축키를 키 코드로 보내고, Enter를 누르기 전에 입력창 내용을 다시 복사해 `/compact`인지 확인한다. 아니면 보내지 않는다.
- **남은 것:** 원인은 추정이다. 그래서 원인을 고치는 것과 별개로 "보내기 전에 확인한다"를 넣었다.

### 압축 직후 카드가 압축 전 크기를 보였다
- **문제:** 압축을 해도 카드의 컨텍스트 크기가 다음 응답 전까지 압축 전 값으로 남았다.
- **원인:** 크기를 마지막 응답의 사용량에서 읽는데 압축 직후에는 새 응답이 없다. 압축 기록에 든 값은 요약 크기뿐이라 실제보다 5만 ~ 10만 토큰 작다.
- **해결:** 요약 크기에 그 세션의 지난 압축에서 본 차이를 더해 어림하고 "약"을 붙여 표시한다.
- **전 → 후:** 압축 직후 표시 295,899(실제 약 10만) → 약 93,095.

### 세션을 열 때마다 읽는 규칙 문서가 너무 컸다
- **문제:** 세션을 열 때마다 커밋 · PR · 위임 규칙까지 모두 읽었다. 대부분의 세션은 그 절을 쓰지 않는다.
- **해결:** 가끔만 필요한 절을 별도 파일로 빼고, 항상 읽는 파일에는 언제 그 문서를 읽는지 한 줄만 남겼다. 나중에는 그 일을 하기 직전에 훅이 보여 주게 바꿨다.
- **전 → 후:** 세션 시작 때 읽는 규칙 문서 30.3KB → 17.8KB(파일 크기 기준 어림. 실제 토큰은 재지 않았다).
